## CONTEXTO

Ya existe un **frontend HTML5/CSS3/JavaScript (ES6+ Vanilla)** de un sistema hospitalario (HIS) que consume una API REST todavía no construida. Tu tarea es generar **solo el backend** (y la capa de conexión a base de datos) que ese frontend necesita, respetando exactamente el contrato de API que ya está escrito en el HTML.

El frontend hace `fetch()` a estas rutas (no las cambies, el frontend ya las llama así):

```
GET  /api/pacientes?q=...
GET  /api/pacientes/:id
GET  /api/pacientes/:id/atenciones
GET  /api/personal?q=...&modo=todo|id|documento|nombre
GET  /api/personal/:id
GET  /api/atenciones?modo=cita|paciente|personal|codigo&q=...&desde=YYYY-MM-DD&hasta=YYYY-MM-DD
GET  /api/atenciones?personal=:idPersonal      (usado para "ver atenciones" de un trabajador)
GET  /api/defunciones?modo=documento|n|cdef|nombre&q=...
GET  /api/busqueda?q=...&tipo=todo|paciente|personal|atencion|defuncion
GET  /api/catalogos/:tabla?q=...
GET  /api/reportes/historial?desde=YYYY-MM-DD&hasta=YYYY-MM-DD
POST /api/pacientes
POST /api/personal
POST /api/atenciones
POST /api/defunciones
```

El frontend espera que las respuestas de listados sean **un array plano** o un objeto `{ items: [...] }` (ambos formatos están soportados en el JS del cliente, pero preferir array plano). Los objetos que hace `openEntity`/`renderEntity` deben tener **exactamente** los mismos nombres de columna que la base de datos (ver esquema abajo), sin renombrarlos ni transformarlos a camelCase.

## STACK TECNOLÓGICO (obligatorio, no cambiar)

**Frontend** (ya existe, no lo regeneres, solo intégralo):
- HTML5, CSS3, JavaScript ES6+ Vanilla, Fetch API.

**Backend:**
- Node.js (LTS más reciente).
- Express.js para la API REST (rutas, controladores, middleware).
- NPM para dependencias.
- Driver oficial **`mssql`** (npm package `mssql`, sobre `tedious`) para conectar con SQL Server. No usar Prisma ni TypeORM: usar consultas parametrizadas directas con `mssql` (`request.input(...)`) para evitar SQL Injection.

**Base de datos:**
- Microsoft SQL Server 2022, base de datos `BDHIS_HRA` (nombre exacto usado por `USE [BDHIS_HRA]` en el script original).

## REGLAS DE NEGOCIO Y VALIDACIÓN

- En los `POST`, valida **longitud máxima** de cada campo `varchar/nvarchar` según el esquema de arriba y rechaza con `400` si se excede.
- Los campos `NOT NULL` de `V_SINADEF_AYACUCHO_DOMFALLECIDO` (todos excepto `EDAD` y `DEBIDO_CAUSA_E`) deben validarse como obligatorios antes del `INSERT`.
- Todas las consultas deben ser **parametrizadas** (`request.input('param', sql.VarChar, valor)`), nunca concatenar strings en el SQL.
- `GET /api/catalogos/:tabla` debe validar `:tabla` contra una **whitelist explícita** de los nombres de tabla listados arriba (para evitar SQL injection vía nombre de tabla dinámico, ya que ahí no se puede parametrizar el identificador).
- Las búsquedas con `q` deben usar `LIKE '%' + @q + '%'` sobre las columnas relevantes (nombre, apellidos, documento, id) según el `modo` recibido.
- Las fechas (`desde`/`hasta`) deben validarse como fechas ISO válidas antes de pasarlas a SQL Server.
- Todas las respuestas de error deben devolver JSON `{ error: "mensaje" }` con el status HTTP correcto (400 validación, 404 no encontrado, 500 error de servidor) y **nunca** exponer el stack trace ni detalles internos de conexión en la respuesta al cliente (sí loguearlos en consola/servidor).

## CONEXIÓN A SQL SERVER

- Usa `dotenv` para leer credenciales desde `.env` (nunca hardcodear usuario/contraseña).
- Variables esperadas en `.env.example`:
  ```
  DB_SERVER=localhost
  DB_PORT=1433
  DB_DATABASE=BDHIS_HRA
  DB_USER=
  DB_PASSWORD=
  DB_ENCRYPT=true
  DB_TRUST_SERVER_CERTIFICATE=true
  PORT=3000
  CORS_ORIGIN=*
  ```
- Crea un **pool de conexión único** reutilizable (`mssql.ConnectionPool`) en `src/config/db.js`, exportado como promesa, y reutilízalo en todos los controladores (no abras una conexión nueva por request).
- Maneja el evento de error del pool y reconexión básica.

- Configura `cors` (usando `CORS_ORIGIN` del `.env`) para que el frontend HTML (servido desde otro origen o `file://`) pueda consumir la API sin bloqueos.

- Usa `morgan` para logging de requests en desarrollo.
- Middleware global de manejo de errores (`errorHandler.js`) al final de la cadena de middlewares en `app.js`.
